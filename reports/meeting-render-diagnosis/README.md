# 렌더 진단 보존 + 고정 구도 재사용 계획

기준 게임 소스 **0fd7564c**, 설치 SDK 8.5.3, Chromium 기본 headless 실행(명시 추가 인자 `--no-sandbox`). 최신 사용자가 연속 이동 개선 대신 고정 구도/만화 패널 방향을 요청했으므로 **게임 코드 수정·새 시안 제작·main 배포를 하지 않았다.** 이 보고서는 기존 후보의 측정과 다음 작은 시안 계획만 보존한다. 새 문구·음성·미선택 효과음도 추가하지 않는다.

## 유효한 측정 결과

동일한 D fixture를 각각 새 브라우저에서 7초 사전 표시 후 다시 열었다. 하나는 녹화 없이, 하나는 기존 canvas/WebAudio MediaRecorder를 켜고 10.5초 관찰했다. Python render 진입 시각/지역 st/객체 ID/함수 소요 시간/실제 view 값을 수집했다. 동시에 requestAnimationFrame 시각도 기록했다. 초기 계측 namespace 오류로 예외 화면을 측정한 시도는 폐기했고 이 폴더에는 정상 화면을 확인한 유효한 두 실행만 포함한다.

| 조건 | 첫 전환 실제 active render | 첫 render 간격 | 반대 전환 active render | 첫 render 간격 |
|---|---:|---:|---:|---:|
| 녹화 없음 | 2회 | 329ms | 1회 | 338ms |
| 녹화 있음 | 2회 | 304ms | 2회 | 250ms |

전환의 명목상 길이는 340ms다. 녹화 없는 첫 전환에서 실제 view는 **0.149 → 2.000**으로 뛰었다. 반대 전환은 **1.885**를 한 번 그린 뒤 다음 호출의 st가 이미 .346초여서 종료 구도로 넘어갔다. 녹화 중에는 **0.182 → 1.999**, 반대 방향 **1.641 → 0.016**만 그려졌다. 프레임 메타데이터와 달리 실제 중간 이동 단계가 거의 없다는 직접 근거다.

- 전환 중 root Python render 소요 최대는 녹화 없음 **10.8ms**, 녹화 있음 **9.8ms**였다. 함수 실행 시간만으로 250~338ms 간격 전체를 설명할 수 없다. GPU/컴포지터/브라우저 메인 루프의 어느 부분이 나머지를 차지하는지는 별도 프로파일을 하지 않아 미확정이다.
- requestAnimationFrame 중앙 간격은 두 조건 모두 16.7ms지만 최대 간격은 **316.6/249.9ms**였다. 전체 환경이 항상 낮은 FPS로 고정된 것이 아니라 전환 부근에 긴 틈이 생겼다.
- 캡처를 끈 상태에서도 긴 간격이 있으므로 **영상 저장만의 문제는 아니다.** 그러나 각 조건 한 번의 관찰이고 환경 부하가 달라질 수 있어, 녹화가 성능을 개선했다거나 캡처 비용이 0이라고 말하지 않는다. 다른 실제 사용자 기기의 성능으로 일반화하지 않는다.
- 측정 구간의 root 객체 ID는 각 실행에서 하나였으며 전환 중 st는 단조 증가했다. 화면 객체 재생성이 이동을 중간에 리셋했다는 근거는 없었다. 초기 준비 중 생성 한 번은 전환 시작 전이다.
- 코드상 active 전환과 인물 레이어는 redraw(0)를 요청하고 있었다. 시간 제한 전에 일부러 redraw를 중단한 경로는 확인되지 않았다. 다음 호출이 늦게 와서 340ms 종료 조건을 넘는 현상이다.
- 배경+일반 인물 레이어의 view도 실제로 변했다. 즉 이 D 후보는 장면을 즉시 바꾼 뒤 잔상만 움직인 것은 아니다. 다만 일반 경로의 `R13_MEETING_SPEED_LINES=True`는 별개로 즉시 목표 시점+짧은 선을 쓰므로 두 경로를 혼동하면 안 된다.

## 이미 있는 고정 구도 기능

- `room13_meeting_seating.rpy:50`의 `r13_meeting_cast`: 회의 참가자/좌석 순서. `:67`의 focus 변경 함수는 현재/이전 화자와 shot revision을 관리한다.
- `room13_meeting_camera.rpy:59`의 `r13_meeting_world_slot`: 좌석 index와 view에서 상대 각도·화면 x·깊이를 계산한다. 현재 C2의 10좌석은 좌석 간 36도다. 초점 인물을 view로 지정하면 그 인물이 중앙에 오는 고정 구도를 재현할 수 있다.
- `R13MeetingOrbit`는 배경, 인물, 탁자 가림을 함께 렌더한다. 검토용 fixed view/레이어 선택도 이미 있으므로 새 카메라 엔진이 필요하지 않다.
- `room13_meeting_direction.rpy:135` 부근의 정확한 대사 cue에는 **뿔이 발언→부리 청자**, **부리 끼어듦→뿔이 청자**가 이미 있다. `r13_meeting_listener`, `r13_meeting_art_slots`, 표정 상태, 실제 반박 공개 token도 재사용할 수 있다.

현재 구현은 **계산으로 재현 가능한 구도**이지 인물별로 따로 승인한 camera preset 저장소나 각도별 그림 파일을 가진 것은 아니다. 고정 구도에서 캐릭터가 새 측면 그림으로 바뀌는 것도 아니다. 보존할 대상은 화면 스크린샷보다 `회의/참가자 순서/초점/표정/승인 art slot` 조합이 적합하다. 사망·부재로 참가자 구성이 달라지면 같은 index를 다른 사람에게 적용하지 않도록 person ID를 기준으로 다시 계산해야 한다. 좌석에 없는 POV 아빠를 index 0으로 조용히 대체하는 방식은 재사용하지 않는다.

## 다음 작은 시안 계획 — 아직 제작하지 않음

**1. 고정 구도 리듬을 기본으로.** 기존 C2 뿔이 발언/부리 청자/부리 끼어들기 cue만 사용해 세 구도를 잇는다. 시점은 정착값으로 바로 잡고, 전환만 컷 또는 0.12~0.18초의 짧은 디졸브를 쓴다. 말하는 사람이 같으면 구도를 유지하고, 청자 반응은 명시된 cue에서만 삽입한다. 원탁 좌석 관계와 화면의 방향을 유지하며 임의 좌우 반전은 하지 않는다. 대사창과 선택 UI는 고정, 읽는 동안은 정지한다. 우선 이 방식을 기본 시안으로 권한다. 짧은 디졸브도 실제 렌더 프레임 검수 없이 부드럽다고 약속하지 않는다.

**2. 반박 순간에만 두 인물 패널.** 기존 두 고정 구도를 인물 중심으로 crop하여 한 인물 패널 위에 상대 패널을 잠깐 겹친다. 새 인물 생성이나 전체 카메라 이동 없이 승인 그림/표정/좌석 구도를 사용한다. 실제 반박 공개 또는 명시적 끼어들기 token에 한 번만 반응하고, 이어지는 발언은 해당 인물의 단일 구도로 돌아간다. 동일 효과를 모든 대사에 반복하지 않는다. 패널의 이름/방향을 일관되게 유지하고 하단 대사·조작 영역을 가리지 않는다. 잔상·새 외침·새 문구·미선택 음향은 합치지 않는다.

두 계획 모두 저장/로드 후 최종 구도 재현, 같은 화자 연속 대사에서 재시작 금지, 빠른 클릭 시 이전 패널 제거, 동작 끔 즉시 정착을 검수 범위로 잡는다. 현재는 제작 보류 상태이며 게임 파일은 0fd7564c와 동일하다.
