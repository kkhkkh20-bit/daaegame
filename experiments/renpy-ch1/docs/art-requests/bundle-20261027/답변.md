## 1. 실제 제작 목록 — 353개 키와 167개 원본의 관계

`room13-field-dot-v2.json` 의 `people` 68명, 자세 키 396개. 그중 `origin=dialogue`(서 있는 그림, 대화 도트판을 1/2 로 되돌린 것) 43개를 빼면
**몸동작 키 353개**가 요청 대상이고, 이 353개가 가리키는 `source.file` 은 **167개**다. 같은 수가 나왔다.

167개 원본 파일을 「몇 개 키가, 어떤 crop 으로 쓰는가」로 나누면:

| 형태 | 파일 수 | 뜻 |
|---|---|---|
| 한 장이 한 자세 | 103 | 그대로 1장 = 1키 |
| 한 파일의 **다른 부분**을 잘라 씀(시트) | 26 | `room13-pixel-acting-*.webp` 같은 여러 칸 시트. 키마다 crop 이 다르므로 각각 별개 그림 |
| 한 파일의 **같은 crop** 을 여러 키가 공유 | 38 | 예: `room13-role-buri-neutral.webp` 의 같은 crop 이 buri `thinking`·`distressed`·`expressive` 세 키. 지금 화면에서 세 자세가 **같은 그림**이다 |

같은 crop 공유 38묶음에 들어 있는 키는 134개(묶음당 3~4개). 그래서 **서로 다른 그림(파일+crop)은 257개**다.
`field-dot-v2/` 결과 webp 의 md5 도 257종이라 일치한다(같은 crop → 바이트까지 같은 결과 파일).

| 구분 | 키 수 |
|---|---|
| 서로 다른 그림(실제로 그려야 할 최소 목록) | **257** |
| 그중 생활·이야기 자세(`living_*`·`map27_*`·`map9_*`·`job_*`·`event_*`·`action_*`·`activity` 등) | 139 |
| 그중 반응 자세(`neutral`·`thinking`·`distressed`·`expressive`, 정면 성분) | 118 |
| 같은 그림을 다른 키로 다시 쓰는 중복 키(모두 반응 자세) | 96 |

주의: 반응 자세 118 + 중복 96 = 214개 키가 `thinking/distressed/expressive/neutral` 이고, 배치표(`FIELD_LIFE_STAGING`) 원칙 1 에 따라
**생활 배치에서는 쓰지 않고 대화 반응에만 쓴다.** 즉 353 중 생활 화면에 실제로 서 있을 그림은 139장이다.

실무 의견으로는, 제작 목록은 **257장(대표 그림)** 으로 넘기고, 중복 96키는 「같은 그림을 다시 가리키기」로 처리한다. 지금도 세 감정이 한 그림이므로
감정별로 따로 그리는 것은 새 기획(각 인물 3감정 몸동작 추가)이지 「다시 찍기」가 아니다. 그것을 원하면 소유자가 따로 정해야 한다.

## 3. 생활 자세 34장 집계와 서리의 자세 ID

요청서 표를 셌다(`현장_생활동작_도트_요청서_20261027.md` 「목록」, `| life_` 로 시작하는 행):
- 공용 동작 11행, 인물을 펼치면 **16장**(돌목·세련 / 여니·누비 / 누비 / 백 부인 / 꽥순·네로 / 네로 / 콩이 / 백 부인·여니·토리 / 칼바람 / 실룩 / 바둑이).
- 인물 전용 **17장**.
- 합 **33장**. 「다시 그릴 기존 자세」 표의 서리 1장을 더하면 **34장**. 코덱스의 해석이 맞다.

배치표(`FIELD_LIFE_STAGING` 맨 끝)는 「공용 17장 + 전용 17장 = 34장」이라고 적었는데 공용은 16장이다. 배치표의 공용 17 은 오기이고, 34 라는 합계는 서리를 세어야 맞는다.
요청서 표 자체에는 서리 행이 없으므로 제작자가 표만 보면 33장을 만든다. **요청서 표에 서리 행을 추가해야 한다.**

서리 자세 ID(지정): **`life_write_desk_seated`** — 진료소 책상(x≈700)에 앉아 기록, 방향 **좌**(책상·우박 쪽), 소품은 진료 기록·붓(`CHARACTER_PROPS.md`).
근거: 배치표 진료소 행 「책상에 앉아 기록(좌)」, 자세 id 규칙 `life_<동작>`. 저장소에 `life_` 로 시작하는 자세 id 는 아직 없으므로 충돌 없음(`game/` 전체 grep).
기존 `living_notes` 는 서서 쓰는 옆모습이라 그대로 두고, `inspect_paper_threequarter_front` 만 이 그림으로 바꾼다.

## 4. 방향·소품·우선순위

### 4-1. 「모두 손에 소품」과 네로 주머니·물결 불쬐기
요청서 공통 규칙은 「손에 일이 있다. 빈손으로 서 있는 자세는 없다」이고, 배치표 원칙 2 는 「그 사람의 직업 소품을 들고 **그 자리의 물건을 대상으로** 한다」이다.
두 동작은 **예외로 적는다**. 대신 소품은 몸에 보이게 한다:
- 네로 `life_wait_hands_pocket`: 손은 주머니. 소품은 `CHARACTER_PROPS` 의 **장갑**(한 짝을 주머니 밖으로 내밀거나 허리띠에 끼움)과 **이름표 꾸러미**(목·허리). 대상 물건은 기대는 벽(창구 옆·문가).
- 물결 `life_warm_hands_fire`: 손은 불 쪽. 소품은 강가 사람의 **밧줄 뭉치**(`map9_rope_coiling` 기존 자세의 것)를 어깨나 발치에. 대상 물건은 벽난로.
이 두 줄을 요청서 공통 규칙 아래에 「예외 2건: 손이 비어도 소품은 몸에 보인다」로 추가하면 된다.
(실무 의견으로는 「모두 손에 소품」을 「소품이 그림에 보인다」로 고치는 편이 제작자에게 덜 혼란스럽다.)

### 4-2. 돌목 등 손질 · 촌장 매듭 세기의 방향

배치표는 소유자 지시로 배경을 보고 만든 것이고 요청서는 그것을 옮긴 것이다. 둘이 다르면 **배경·코드와 맞는 쪽이 기준**이다. 확인 결과:

**돌목 `life_lamp_trim`** — 요청서 **우**, 배치표 **좌**(돌목 행 「향함 좌(명부·손님 쪽)」, 저녁 등 손질 포함).
- 배경 `assets/room13-pixel-ready-gate0173-afternoon.webp`(2048×768, 자리표 폭 1920 기준 ×1.067) 을 봤다. 초소 등은 **초소 왼쪽 기둥에 걸려 있다**(그림 x≈1390 → 자리표 x≈1300). 창구(책 펼친 선반)는 그 오른쪽 x≈1340~1550.
- 배치표대로 돌목이 「창구 안쪽」에 서면 등은 **왼쪽**에 있다 → **좌가 맞다. 요청서의 우는 오기.**
- 다만 지금 코드의 돌목 자리는 `R13_STAND_SPOTS["gate"]` 의 `[1234,592]`(문기둥 옆, 등보다 왼쪽) 라 거기서 보면 등은 오른쪽이다. 배치표 후속(돌목을 창구 안으로)을 하면 좌로 맞는다. 그림은 좌 한 방향만 받고, 자리를 옮기기 전까지는 좌우 반전 — 단, **현장 인물 좌우 반전은 아직 코드에 없다**(`room13_acting.rpy`·`room13_v111_field_layout.rpy`·`room13_field_dot.rpy` 에 `xzoom`/flip 없음). 배치표 「우리 쪽 후속」에 들어 있는 일이다.

**촌장 `life_count_knots`** — 요청서 **우**(자리 「광장 장작, 시장 아치」), 배치표 광장 **우(장작)**, 시장 **뒤**.
- 광장은 둘이 같다(우). 다른 곳은 시장 행뿐이다. 한 그림은 한 방향이므로 시장의 「뒤(3/4 뒷모습)」는 좌우 반전으로 만들 수 없다.
- 시장 배경(`room13-pixel-wide-market-afternoon.webp`, 2172×724)을 보면 **장작은 왼쪽 화덕 가게 앞(x≈360~480)** 에 있고 아치(x≈1085) 앞에는 장작이 없다. 매듭 끈으로 장작을 세는 동작은 아치보다 장작 앞이 맞다.
- **기준은 우(광장 행 = 요청서).** 배치표 시장 행의 「아치·뒤」는 오기로 보고 「화덕 가게 장작 앞, 우」로 고쳐 적는다. 실무 의견으로는 이렇게 하면 2장이 아니라 1장이다.

### 4-3. P1 — 문서 목록인가, 실제 1~3일 등장 전부인가
요청서 P1 은 16장 + 서리 = 17장이다. 실제 1~3일에 보이는 동작을 재구성해 봤다.
방법: `room13_rules.rpy` `r13_where` 의 고정 규칙 + `room13_life.rpy` `R13_WEEKLY_ROUTINES`(없으면 `room13-content.json` `weekly_locations`) 로 1~3일 × 아침·낮·저녁 × 장소를 계산했다(`05_생활동작/1~3일_등장_재구성.json`).
**이것은 정적 표의 재구성이지 엔진 덤프가 아니다.** 배치표가 썼다는 「엔진 덤프 r13_stage_people(10일×3시간대×20장소)」는 저장소에 없다. 사건 상태·`new_places` 이동·`R13_RELOCATE`·돌목 핀 등 동적 규칙은 뺐다. 따라서 아래는 「배치표의 날짜 열 + 정적 일정」 기준이다.
