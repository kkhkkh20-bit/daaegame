# 회의 「다시」 로직 연결 (0.20.33)

기존 승인 화면의 accept/retry 선택을 실제 회의 기회 소진에 연결했다. 패배 결과·생사·명단 변경을 적용하기 전에 선택창을 띄운다. 「받아들인다」는 기존 결과로 이어지고, 「다시」는 그 회의 첫 쟁점 직전으로 돌아간다.

## 구현 범위

- `room13_meeting_retry_logic.rpy`의 한 표에 회의 11개의 재시작 라벨을 둔다: 입구, 등, 5일 입구, 불, 13호, 기록, 가설, 수프, 담요, 피코, 제단.
- 첫 쟁점 직전 `room13`와 `v111_` 진행 변수를 복사한다. 기회·쟁점·제시 근거·남겨 둔 근거·적용 표식·속말 대기를 복원한다.
- 회의 전 얻은 자료·생사·명단·다른 회의 결과는 시작 당시 상태로 보존한다. 회의 중 얻은 자료도 시작 당시로 돌아가며, 다시 진행하면서 얻는다.
- 재시도는 새 호출을 쌓지 않고 첫 쟁점 라벨로 이동한다. 같은 회의에서 다시 기회를 다 쓰면 다시 선택할 수 있다.
- 새 판에서는 체크포인트를 초기화한다. 아침 복구는 기존 전체 저장 불러오기를 사용하므로 해당 시점의 체크포인트도 함께 복구된다.
- 구형 회의 도중 저장에 체크포인트가 없으면 기존 결과 흐름을 유지한다. 이미 기회를 쓴 구형 저장의 첫 쟁점 재진입에서도 불완전한 상태를 새 시작점으로 저장하지 않는다.
- UI 디자인·정답 판정·결말 조건은 변경하지 않았다.

## 네이티브 검증

Ren’Py 8.5.3, Xvfb 1280×720에서 실제 오답 라벨을 실행했다. fixture는 기회를 소진 직전으로 준비하고 기존 화면 버튼을 눌러 확인한다. 전체 자연 플레이 결과로 주장하지 않는다.

3일·10일·11일의 첫 쟁점 복귀, 기회 복구, 기존 자료 유지와 임시 근거·적용 표식 삭제를 확인했다. 3일은 두 번 재시도하고 반환 스택 깊이가 늘지 않는지 확인했다. 받아들임은 가설 회의 lose로 이어지는지 확인했다. 기존 5일·10일의 부분 정답 뒤 패배 흐름도 통과했다.

로그 원문은 `logs/`, 실제 화면 캡처는 `screens/`에 있다. 전체 단위·lint·웹 빌드·브라우저 및 공개 결과는 최종 릴리스 기록을 따른다.
